# Instagram Reels 与播放器评论支持需求分析、实施方案和验收标准

编制日期：2026-09-14

建议目标版本：`v0.2.31`

状态：**A-I 裁定项已全部采用推荐意见；需求已审核通过，编码已启动**

## 1. 建设目标

在现有 Bilibili、YouTube、抖音、TikTok 和小红书支持基础上，新增 Instagram（简称 Ins）站点，并在播放器右侧播放列表滑窗中增加评论 Tab。

本需求包含两个可以独立验收、但共享 Cookie、异步任务和播放器上下文的部分：

1. Instagram Reels 首页、搜索、视频播放和下载等多站点基础能力；
2. 播放器右侧面板的“播放列表 / 评论”双 Tab，以及当前视频评论的懒加载、分页和错误状态。

目标不是把 Instagram 或评论接口硬编码成一组永久有效的 HTTP 请求。Instagram、抖音、TikTok、小红书都可能同时校验登录 Cookie、设备指纹、页面运行环境、动态签名、访问节奏和地区，因此首版必须保留浏览器安全上下文和能力降级路径。

## 2. 当前项目能力盘点

### 2.1 站点接入框架

当前站点由 `services/site_registry.py` 集中注册，配置、Cookie、默认画质、首页缓存、URL 识别和工具栏标签均按 `SITE_KEYS` 数据驱动。解析和下载主链路由 `resolver/site_resolver.py`、`resolver/youtube_resolver.py`、`download/` 和 `ui/main_window.py` 协同完成。

新增 Instagram 时必须同时审计以下固定站点分支，不能只新增一个 `SiteDefinition`：

- URL host 和 URL 类型识别；
- 首页、搜索、作者列表和播放列表入口；
- Cookie 文件、浏览器 Profile 和自动检测；
- `VideoInfo`、`HomeVideo`、`PlaylistEntry` 的来源标识和稳定 ID；
- 下载任务恢复、收藏、历史和播放记忆；
- 默认画质、代理、备份恢复、错误提示和关于页文案；
- 播放器右侧面板的可用内容与加载状态。

### 2.2 yt-dlp 与评论能力

当前项目内置 yt-dlp 版本为 `2026.08.19`。该版本命令行提供 `--write-comments` / `--get-comments`，但这只是“允许提取评论”，实际是否返回评论取决于具体 extractor、登录状态和平台响应。

因此评论能力应采用三层策略：

1. **yt-dlp 优先**：对 extractor 能稳定返回 `comments` 字段的平台，复用现有 Cookie、代理和日志脱敏机制；
2. **站点浏览器服务**：对需要页面签名、GraphQL、动态 token 或浏览器上下文的平台，使用站点已有或新增的 WebEngine 服务请求评论；
3. **明确不可用**：请求失败、未登录、平台不返回评论或当前内容权限不足时，Tab 显示可解释状态，不伪造空评论，也不阻塞视频播放。

### 2.3 右侧播放列表面板

`ui/playlist_overlay.py` 当前是一个可从播放器右侧热点滑出的 `PlaylistOverlay`，内容包含标题、作者列表、已保存列表、自动连播、播放和下载操作。播放器通过 `PlayerPage._handle_mouse_move()` 处理右侧热点，作者播放列表通过 `MainWindow._schedule_creator_playlist()` 异步生成，并已有 loading 状态和“播放列表加载中，请稍候”提示。

评论 Tab 应建立在这个覆盖层之上，避免另起一套侧滑窗口。评论加载必须和作者列表 worker、合集 worker 使用不同的 generation/request id，不能互相取消或覆盖。

## 3. Instagram 平台可行性分析

### 3.1 地址与内容类型

Instagram Reels 首页地址为：

```text
https://www.instagram.com/reels/
```

建议支持的单视频地址包括：

```text
https://www.instagram.com/reel/<shortcode>/
https://www.instagram.com/p/<shortcode>/
https://www.instagram.com/tv/<shortcode>/
```

其中 `/p/` 可能是图文、轮播或视频，必须根据详情数据过滤出可播放视频；不能仅凭 URL 路径把所有帖子当成视频。

作者页面、标签页、分享短链和登录跳转地址的行为受当前会话影响，首版只在真实验证通过后启用对应 URL 类型。分享短链的重定向不能成为 Reels 首页实现的依赖。

### 3.2 首页与搜索

`/reels/` 是登录相关的动态推荐页面，不是稳定的 yt-dlp 播放列表 URL。推荐使用独立的 Instagram WebEngine 服务加载官方页面，并在同源环境读取卡片数据或调用页面已有接口：

- 首次加载使用 Firefox/Chromium Cookie 和独立 Profile；
- 卡片保留 shortcode、原始 URL、作者昵称、封面、时长、发布时间和必要的页面上下文；
- 对图文、广告、直播、推荐占位项和缺少媒体信息的卡片进行过滤；
- 页面滚动或官方接口分页后，在应用内按 20 条有效视频切页；
- 请求设置总时长、批次和并发上限，遇到登录页、验证码或风控立即停止并提示用户；
- 卡片媒体 URL、页面 token 和动态签名只保留在短期内存上下文，不写入持久缓存。

Instagram 搜索不像 Bilibili 搜索那样有稳定公开接口。首版建议使用 Instagram 官方搜索页面作为发现入口，读取搜索结果中可识别的 Reel/视频帖子；如果页面只返回用户或标签而没有稳定的视频卡片，则显示“当前搜索结果没有可播放视频”，不回退到其它站点，也不伪造分页。

### 3.3 播放、下载与 Cookie

单视频详情优先交给 yt-dlp `Instagram` extractor 解析。解析上下文必须包含：

- Instagram 专用 Cookie 文件或浏览器 Cookie；
- 当前卡片的原始 URL 和必要的页面参数；
- 页面返回的 Referer、User-Agent 和 Origin；
- 当前代理设置。

解析成功后将裸 shortcode 转换成稳定业务 ID，例如 `instagram:<shortcode>`，用于下载、收藏、历史和播放记忆。签名媒体 URL 不能长期保存；下载任务发现 URL 过期时最多重新解析一次。

清晰度沿用现有 `VideoQuality` 选择规则。Instagram 可能只返回单条混合流，也可能返回多个尺寸或 HLS 清单；首版应支持实际返回的格式，不承诺所有 Reel 都有 1080p。

### 3.4 作者播放列表与合集

Instagram 作者页和 Reels tab 的内容依赖登录会话和页面接口，不能默认承诺作者列表一定可用。建议首版将作者昵称作为强交付，作者其它视频列表在页面数据真实可读时启用；未获取到列表时保留单视频播放，不显示误导性的空列表。

## 4. 完善后的功能需求

### R1：Instagram 站点注册与排序

Instagram 必须放在 TikTok 之后、小红书之前，推荐定义如下：

| 项目 | 推荐值 |
| --- | --- |
| 内部键 | `instagram` |
| 显示名 | Instagram |
| 紧凑标签 | I |
| 主站 host | `instagram.com` |
| 首页 | `https://www.instagram.com/reels/` |
| Cookie 文件 | `cookie_instagram.txt` |
| 默认画质 | 按站点独立保存 |
| 播放列表 | 支持作者列表时启用，否则仅单视频 |

站点顺序应为：

```text
Bilibili → YouTube → 抖音 → TikTok → Instagram → 小红书
```

Instagram 的 Cookie、自动检测结果、Profile、缓存指纹、默认画质、收藏、历史、下载来源和播放记忆必须与其它站点隔离。工具栏缩写应在窄窗口下完整显示。

### R2：Instagram 首页 Reels

1. 首页选择 Instagram 后加载官方 Reels 页面或同源数据。
2. 只显示可识别为视频的 Reel/帖子，过滤图文、轮播、广告、直播和占位项。
3. 每个完整 UI 页目标为 20 条有效视频，同页和当前会话跨页尽量去重。
4. 采用页面滚动或官方游标继续取数，设置批次数、总时长和并发上限。
5. 平台返回不足 20 条、要求登录或触发风控时，保留已获取内容并显示具体原因。
6. 卡片至少显示封面、标题/描述、作者昵称、来源和可获得的时长。
7. 卡片内存上下文保留 shortcode、原始 URL 和解析所需安全参数，点击播放不能丢失。
8. 切换站点后再返回 Instagram 时恢复缓存的完整页面和页码；缓存不保存 Cookie、动态签名和长期媒体 URL。

### R3：Instagram 搜索

1. 工具栏搜索框在 Instagram 站点下只搜索 Instagram。
2. 优先读取官方搜索页面中的视频帖子，不把用户、标签或图文结果送入播放器。
3. 支持站点实际提供的分页/滚动；无法稳定分页时显示真实已加载数量和“没有更多可用视频”。
4. 搜索请求必须可取消，关键词、站点、Cookie、代理变化后旧结果不得覆盖新结果。
5. 无结果、未登录、风控、网络错误和“只有非视频内容”使用不同提示。

### R4：Instagram URL 播放、下载与数据列表

1. 支持 `/reel/<shortcode>`，并在真实验证通过后支持视频型 `/p/<shortcode>`。
2. 详情解析优先复用 yt-dlp；失败时允许同一浏览器会话内重取一次详情上下文。
3. 稳定视频 ID 使用 `instagram:<shortcode>`，来源始终显示 Instagram。
4. 播放、暂停、Seek、音量、全屏、小窗、停止、自动连播和播放记忆沿用现有播放器。
5. 下载任务保存来源站点、原始 URL、必要请求头和可重新解析的上下文标识，不保存过期签名 URL 作为唯一恢复依据。
6. 收藏、历史、下载列表和备份恢复都能显示 Instagram 来源，旧站点数据不受影响。
7. 作者昵称优先使用页面显示名；用户名只在昵称缺失时作为回退。

### R5：评论 Tab 的交互

1. 播放器右侧滑窗顶部增加两个 Tab：`播放列表`、`评论`。
2. 默认打开 `播放列表`，保持现有右移滑出、互斥、自动隐藏和小窗禁用侧栏行为。
3. 用户首次切换到“评论”Tab 时才开始加载当前视频评论，不因进入播放器就阻塞首帧播放。
4. 评论加载期间显示“评论加载中，请稍候”，鼠标继续移动不会重复创建请求。
5. 加载成功后以列表显示：作者昵称、评论正文、发布时间、点赞数；头像、回复数和回复列表仅在数据源稳定提供时显示。
6. 评论文本按纯文本渲染并限制长度，禁止未经清洗的 HTML、脚本和外链资源进入 UI。
7. 支持“加载更多”或滚动分页。每次请求有上限，不能因鼠标移动或滚动重复发起相同页。
8. 评论 Tab 不提供发表评论、点赞、回复、删除或账号操作；需要这些操作时交给官方浏览器页面。
9. 切换视频、停止播放、退出小窗或关闭应用时取消旧评论请求；旧请求迟到结果不得写入新视频。
10. 当前视频没有评论、未登录、评论权限受限、触发风控和接口不支持时显示对应状态及可行建议。

### R6：评论来源与站点能力降级

建议按下表作为首版能力目标，最终以真实环境和平台接口验证为准：

| 站点 | 首选来源 | 备用来源 | 首版承诺 |
| --- | --- | --- | --- |
| YouTube | yt-dlp `comments` | 官方页面/浏览器上下文 | 已登录且 extractor 返回时显示评论 |
| Bilibili | 官方评论 API/页面数据 | yt-dlp 或页面回退 | 视频评论可分页加载 |
| 抖音 | 内置浏览器签名接口 | 官方页面上下文 | 登录且通过风控时显示评论 |
| TikTok | 浏览器页面接口 | yt-dlp（若返回） | 登录、地区允许且接口可读时显示 |
| Instagram | 官方页面 GraphQL/页面数据 | yt-dlp（若返回） | 登录且页面返回评论时显示 |
| 小红书 | 内置浏览器页面接口 | 无 | 真实接口验证稳定后启用，否则明确不可用 |

“支持评论”定义为：请求链路、状态展示、取消和降级完整；不把平台暂时拒绝评论误报成程序故障，也不要求所有站点在所有账号和地区都必须返回评论。

### R7：评论数据模型、缓存与隐私

建议新增独立模型，不复用 `PlaylistEntry`：

```text
CommentInfo
  comment_id
  video_id
  source_site
  author_name
  author_id（可选）
  avatar_url（可选）
  text
  like_count（可选）
  reply_count（可选）
  created_at（可选）
  parent_id（可选）
  position
```

缓存键至少包含站点、稳定视频 ID、Cookie/账号摘要、代理摘要和分页游标。建议只在内存保存评论，或使用短 TTL 的脱敏缓存：

- 不保存 Cookie、Authorization、动态签名和完整 GraphQL 请求；
- 不把评论原文写入普通日志；
- 日志只记录站点、视频 ID、页码、原始数量、保留数量、耗时和错误类别；
- 文本显示前做 HTML/控制字符清洗和最大长度截断；
- 账号、视频和评论切换后清除不属于当前上下文的缓存结果。

### R8：并发、取消与性能

1. 评论加载使用独立 `CommentsWorker` 或站点服务异步任务，不占用当前视频解析 worker。
2. 每个视频同时只允许一个首屏评论请求和一个“加载更多”请求。
3. 播放列表作者 worker、合集 worker、评论 worker 各自使用 generation/request id。
4. 切换视频或停止播放立即使旧评论请求失效；网络层无法中断时也必须丢弃迟到结果。
5. 评论首屏建议限制为 20 条，单次更多请求不超过 20 条，最多保留可配置上限。
6. 评论请求不得拖慢视频播放、控制器显示、右侧面板动画和小窗操作。
7. 连续失败或命中风控后进入短暂冷却，用户可手动重试一次；不得无限重试。

## 5. 推荐实施方案

### 阶段一：站点基础接入

1. 扩展站点注册表、配置默认值、Cookie 自动检测、工具栏排序和来源显示。
2. 增加 Instagram URL 识别、短视频稳定 ID 和站点隔离测试。
3. 增加 Instagram WebEngine 服务，完成 `/reels/` 页面加载、Cookie 注入、卡片提取、滚动补水、风控/登录状态识别和请求取消。

### 阶段二：解析、播放与数据链路

1. 在 resolver 中增加 Instagram 首页、搜索、详情和作者列表适配。
2. 让卡片上下文优先进入 yt-dlp 解析，补齐 Referer、Cookie、Origin 和 User-Agent。
3. 接入下载、收藏、历史、播放记忆、默认画质、备份和错误提示。
4. 在真实 Firefox Cookie 环境分别验证 Reels 首页、搜索、至少 10 个视频播放和至少 5 个下载任务。

### 阶段三：评论抽象与右侧 Tab

1. 新增 `CommentInfo`、评论状态枚举和站点评论能力描述。
2. 将 `PlaylistOverlay` 内容区改为 `QTabWidget`，播放列表 Tab 保留现有控件和布局。
3. 新增评论列表组件、加载中/空态/错误态/加载更多控件和纯文本清洗。
4. 新增独立评论 worker、request id、取消和缓存层。
5. 先接入 YouTube、Bilibili 两个可验证链路，再按真实接口稳定性接入抖音、TikTok、Instagram 和小红书。
6. 评论 Tab 在小窗模式下继续隐藏；普通播放器中不因评论请求改变视频播放状态。

### 阶段四：真实环境和回归验证

1. Firefox 分别登录 Instagram、YouTube、Bilibili，并关闭/保持浏览器运行两种状态测试 Cookie 读取。
2. 对不同视频类型测试：Reels、视频型帖子、图文帖子、无评论视频、评论受限视频和已删除视频。
3. 测试快速切换视频、切换站点、停止、进入/退出小窗、重复打开评论 Tab、加载更多和网络断开恢复。
4. 验证普通安装版与开发版使用相同的 yt-dlp、JS Runtime、Cookie 和资源定位策略。

## 6. 验收标准

### A. Instagram 基础能力

- 工具栏顺序为 `B → Y → D → T → I → X`，Instagram 缩写完整显示。
- Firefox 已登录 Instagram 时，能够加载 `/reels/` 首页；无登录或风控时显示明确提示。
- 首页成功展示的卡片均为可识别视频，不出现图文、广告和无封面占位项。
- 至少完成 3 页首页滚动/分页测试；同页无重复，页间重复率符合实现说明。
- 至少 3 个关键词搜索有结果或显示真实的“无可播放视频/需登录/风控”状态，不回退到其它站点。

### B. Instagram 播放与下载

- 至少播放 10 个 Reels/视频帖子，其中横屏、竖屏和不同清晰度各有样本。
- 播放器显示正确的 Instagram 来源、标题、作者昵称和可用清晰度。
- 至少下载 5 个视频，完成文件立即可在下载列表播放，来源显示 Instagram。
- 收藏、历史、播放记忆、自动连播和小窗不回归。
- 图文/轮播非视频地址显示“当前仅支持视频内容”类提示，不显示误导性的“没有可播放清晰度”。

### C. 评论 Tab

- 右侧面板显示 `播放列表` 和 `评论` 两个 Tab，默认仍打开播放列表。
- 切换到评论后首屏在限定时间内进入成功、空态或错误态；加载过程不影响视频播放。
- 评论展示作者、正文和可用的时间/点赞信息，HTML 和脚本不会被执行或原样注入。
- “加载更多”不重复、不乱序、不覆盖旧评论；到达末页后禁用或隐藏控件。
- 切换视频、停止播放和关闭应用后，旧评论结果不会出现在新视频中。
- 评论请求失败时保留重试入口，并区分未登录、风控、权限限制、网络失败和平台不支持。
- 小窗模式下播放列表和评论 Tab 都不会滑入，退出小窗后右侧面板状态正常恢复。

### D. 隐私、稳定性和性能

- Cookie、Authorization、动态 token、评论正文和完整媒体签名不写入普通日志。
- 首页、搜索、播放、评论请求均有超时、取消、并发上限和旧结果丢弃机制。
- Instagram 与评论功能失败不能阻塞其它站点首页、视频播放、下载和应用启动。
- 普通安装版、便携版和开发版的站点识别、yt-dlp、Node/Deno 和 Cookie 路径行为一致。
- 自动化测试覆盖站点注册、URL 识别、Cookie 隔离、评论模型、Tab 交互、请求取消和数据清洗。
- 全量测试、编译检查、静态检查和 `git diff --check` 通过。

## 7. 风险与边界

1. Instagram、抖音、TikTok、小红书的页面结构和评论接口可能随时变化，无法承诺永久稳定。
2. Cookie、账号地区、IP、设备指纹和访问节奏会影响首页、播放和评论返回结果。
3. yt-dlp 的 `--write-comments` 不是所有 extractor 都实现；评论 Tab 必须允许站点级不可用。
4. Instagram 搜索和 Reels 首页更接近登录网页发现流，不应承诺与官方客户端完全一致的推荐数量和排序。
5. 评论正文、头像和时间字段可能缺失或被平台脱敏，UI 应以可用字段为准，不用占位内容冒充真实数据。
6. 本需求不包含发表评论、点赞、回复、私信、账号登录、批量评论导出和评论情感分析。
7. 真实环境验证需要用户已登录的 Firefox Instagram/YouTube/Bilibili Cookie；自动化测试只能覆盖离线数据形状和状态转换。

## 8. 用户裁定结果

以下 A-I 项已由用户裁定为全部采用推荐意见：

| 项目 | 最终裁定 |
| --- | --- |
| A. Instagram 首页形态 | 保留统一原生卡片首页，使用浏览器上下文取 Reels 数据；官方网页作为风控/接口不可用时的后备入口 |
| B. Instagram 搜索 | 优先读取官方搜索页中的视频帖子；无法稳定分页时展示实际数量，不用重复卡片凑数 |
| C. 评论首批站点 | 先实现 YouTube、Bilibili，再按真实接口稳定性接入抖音、TikTok、Instagram、小红书 |
| D. 评论加载时机 | 仅在用户切换到评论 Tab 时懒加载；播放列表 Tab 默认不触发评论请求 |
| E. 评论分页 | 首屏 20 条，使用“加载更多”或滚动到底部触发下一页，每视频请求有上限 |
| F. 评论缓存 | 默认只做内存短 TTL 缓存，不持久化 Cookie、token 和评论正文 |
| G. 评论交互 | 只读展示，不提供发表评论、点赞、回复和删除；互动统一交给官方浏览器 |
| H. 评论不可用状态 | 明确显示未登录、风控、权限限制、网络失败或平台不支持，保留手动重试 |
| I. 版本节奏 | Instagram 基础能力与评论 Tab 分阶段交付，评论不阻塞 Instagram 播放/下载首版 |

## 9. 建议验收顺序

1. 先审核站点顺序、Cookie 隔离、Instagram 首页形态和搜索降级规则。
2. 再审核评论 Tab 的懒加载、首批站点、分页、缓存和只读边界。
3. 编码后先完成离线单元测试，再进行 Firefox Cookie 真实环境验证。
4. 真实环境通过后更新 README、release note、版本号并执行发布流程。
