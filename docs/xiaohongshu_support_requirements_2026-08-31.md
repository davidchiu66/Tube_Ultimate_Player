# 小红书视频支持需求分析、实施方案和验收标准

编制日期：2026-08-31

建议目标版本：`v0.2.31`

状态：**用户已审核通过；功能编码、自动化测试和真实 Firefox Cookie 验证已完成**

## 1. 建设目标

在现有 Bilibili、YouTube、抖音和 TikTok 支持基础上，增加独立站点“小红书”，并以小红书视频频道作为首页内容来源：

```text
https://www.xiaohongshu.com/red_video
```

用户原始地址末尾包含中文逗号，该标点不属于 URL；程序和文档统一使用上述规范地址。

“加入小红书支持”不能只理解为增加一个首页按钮。为了与当前应用的多站点体验一致，推荐首版贯通以下业务链路：

- 小红书视频首页；
- 视频搜索；
- 小红书视频笔记 URL 播放；
- 清晰度选择、播放、下载；
- 收藏、历史、播放记忆；
- 每站点独立 Cookie、默认画质和默认首页；
- 来源识别、显示标签、备份恢复和错误提示；
- 在真实安装版中验证资源、Cookie 和 WebEngine 运行环境。

小红书图文笔记、直播、评论、私信、商城和账号登录不属于本需求。

## 2. 地址语义与平台能力核实

### 2.1 地址类型

`https://www.xiaohongshu.com/red_video` 是小红书的视频频道/推荐流首页，不是单视频地址。

当前确认的单篇笔记地址形式包括：

```text
https://www.xiaohongshu.com/explore/<note_id>
https://www.xiaohongshu.com/discovery/item/<note_id>
```

首页和搜索卡片还会携带 `xsec_token`。该令牌与页面安全上下文有关，对后续详情页访问和视频解析的可靠性有直接影响，因此不能只保存裸 `note_id` 后丢弃卡片上下文。

小红书分享短链常见于 `xhslink.com`。其重定向目标、有效期和登录要求尚未完成系统验证，推荐纳入首版 URL 兼容测试，但不作为首页实现的依赖。

### 2.2 项目内置 yt-dlp 能力

项目内置 `3rdpart/yt-dlp.exe` 版本为 `2026.07.04`，已包含 `XiaoHongShu` 提取器。其 URL 匹配范围仅为：

```text
https://www.xiaohongshu.com/explore/<note_id>
https://www.xiaohongshu.com/discovery/item/<note_id>
```

实测结论：

1. `red_video` 首页会得到 `Unsupported URL`，说明 yt-dlp 不能承担首页发现和分页。
2. 只有裸 `explore/<note_id>`、缺少有效页面上下文时，样本可能得到 `No video formats found`。
3. 使用 Firefox 已登录 Cookie，并保留首页卡片返回的有效 `xsec_token` 后，同一样本可以正常解析。
4. 样本解析出了 H.264、HEVC、多帧率和多个分辨率，最高验证到 `1440 x 2560`。
5. 当前提取器只返回 `uploader_id`，没有稳定提供作者昵称、作者主页或作者视频列表。

因此，yt-dlp 适合继续承担“单视频详情页到媒体格式”的解析，不适合单独承担首页、搜索、作者列表和安全验证。

### 2.3 首页真实数据链路

普通 HTTP 请求可以下载 `red_video` 的 SSR 页面，但初始状态中的推荐列表为空；真实内容在浏览器 JavaScript 运行后通过签名接口取得。

当前真实环境观察到的首页接口为：

```text
GET https://edith.xiaohongshu.com/api/sns/web/v1/common/dual_feed
```

首批请求包含以下分页相关参数：

```text
cursor_score=
scene=feature_feed
num=30
refresh_type=1
note_index=0
need_num=10
```

后续请求使用服务端返回的 cursor，并将 `refresh_type` 调整为后续加载模式。响应中已确认存在：

```text
data.result
data.next_cursor
data.has_no_more
data.data[]
```

一次真实响应包含 20 个卡片项。卡片可提供：

```text
id
type
title
desc
user
images_list
xsec_token
liked_count
track_id
```

其中视频卡片使用 `type = "video"`。卡片响应本身不直接等同于最终可播放媒体流。

### 2.4 搜索真实数据链路

当前真实环境观察到的搜索接口为：

```text
POST https://so.xiaohongshu.com/api/sns/web/v2/search/notes
```

浏览器实际请求体包含：

```text
keyword
page
page_size
search_id
session_id
sort
note_type
image_formats
```

实测 `page_size=20`，响应包含：

```text
data.items[]
data.has_more
```

搜索条目包含 `id`、`model_type`、`note_card` 和 `xsec_token`。接口可能混入图文笔记或其它展示项，因此适配层必须按实际笔记类型过滤视频，并在请求预算内从后续批次补足页面，不能把图文卡片送入播放器。

### 2.5 Cookie 与安全上下文

当前 Firefox Profile 已能读取到小红书域 Cookie，并能成功加载视频首页。样本中存在 `web_session`、`id_token`、`a1` 等 Cookie 名，证明当前按浏览器导入 Cookie 的方案可复用。

直接使用 Python HTTP 加 Cookie 调用详情接口仍可能返回 HTTP 406；页面脚本还会加载动态安全组件。由此可见，小红书会同时校验 Cookie、浏览器运行环境、页面生成的请求参数/请求头和访问上下文。

结论：不能把小红书实现为一组脱离浏览器环境的固定 HTTP 请求，也不应在代码中硬编码或长期缓存动态签名。

## 3. 完善后的功能需求

### R1：站点注册与基础配置

新增独立站点定义：

| 项目 | 推荐值 |
| --- | --- |
| 内部键 | `xiaohongshu` |
| 显示名 | 小红书 |
| 紧凑名 | XHS |
| 主站 host | `xiaohongshu.com` |
| 分享短链 host | `xhslink.com`，真实验证后启用 |
| 首页 | `https://www.xiaohongshu.com/red_video` |

小红书必须独立保存：

- 默认画质；
- Cookie 文件；
- Cookie 浏览器和 Profile；
- 首页、搜索和播放详情缓存；
- 默认首页选择；
- 收藏、历史、播放记忆和下载来源。

新增站点后不得使未识别地址回退并错误标记为 YouTube。

### R2：视频首页

1. 工具栏增加“小红书”站点，切换后加载 `red_video` 的视频推荐流。
2. 首页只显示真实视频笔记，过滤图文、直播、商品、话题、用户推荐、占位项和缺少有效 ID/封面的脏卡片。
3. 卡片至少显示标题、作者昵称、封面和来源；点赞数、时长和发布时间仅在数据源可靠提供时展示。
4. 首页使用服务端 cursor、`note_index` 和 `has_no_more` 分页，不伪造页码 offset。
5. UI 标准页容量为 20 条；一个接口批次不足 20 个有效视频时，可在严格请求预算内继续取下一批并去重。
6. 同页不得出现重复 `note_id`；当前浏览会话中跨页也应尽量去重。
7. 平台未返回足够视频、需要验证或请求预算耗尽时，不用重复卡片和图文卡片凑数，应保留当前页并显示明确状态。
8. 切换站点再返回时恢复小红书当前页、结果和滚动状态。
9. 首页卡片必须在内存中保留 `note_id + xsec_token + xsec_source`，供点击播放时构造可靠详情 URL。

### R3：搜索

1. 在小红书站点下使用顶部搜索框时，只搜索小红书内容，不回退到其它站点。
2. 搜索只输出视频笔记，过滤图文笔记和不可播放展示项。
3. 使用平台返回的 `search_id`、页码和 `has_more` 继续分页，不复用旧关键词会话。
4. 每个成功展示的完整页面目标为 20 个有效视频；补足过程必须有请求次数和时间上限。
5. 用户更换关键词、切换站点或关闭应用时，取消旧搜索任务，旧响应不得覆盖新结果。
6. 搜索结果缓存键至少包含站点、关键词、页码、Cookie/代理指纹和搜索会话。
7. 无结果与风控、未登录、网络失败必须使用不同提示。

### R4：视频 URL 识别与播放

1. 支持 `/explore/<note_id>` 和 `/discovery/item/<note_id>` 视频笔记 URL。
2. 支持首页/搜索卡片生成的带 `xsec_token` URL。
3. 对 `xhslink.com` 分享短链先进行受控重定向，再识别最终小红书地址；真实验证不通过时不宣称正式支持。
4. 图文笔记 URL 应提示“当前仅支持小红书视频笔记”，不得显示“没有可播放清晰度”。
5. 优先把带安全上下文的详情 URL交给项目内置 yt-dlp 提取器，复用现有格式整理、Cookie、代理、字幕和下载上下文能力。
6. yt-dlp 解析前必须使用小红书站点 Cookie；不得误用 YouTube、抖音或默认首页站点 Cookie。
7. 首页/搜索卡片点击播放时优先复用当前卡片上下文，不能先丢弃 token 再用裸 URL 重抓详情。
8. token 失效时，允许在同一 WebEngine 会话中重新获取详情上下文后重试一次；不得无限重试。
9. 播放必须保留媒体所需的 User-Agent、Referer、Cookie 和其它已验证请求头。
10. H.264、HEVC、不同分辨率和帧率映射为稳定清晰度选项；同分辨率多编码格式按当前质量选择规则排序。
11. 默认画质支持智能、高、中、低，并按小红书独立保存。
12. 播放、暂停、Seek、音量、全屏、小窗、停止、重新播放和自动连播沿用现有播放器行为。

### R5：下载

1. 单视频下载复用成功解析后的 `VideoInfo/raw_info` 和小红书 Cookie 上下文。
2. 下载任务保存 `source_site=xiaohongshu`，列表显示“小红书”。
3. 下载前发现 token 或媒体 URL 失效时，重新解析一次详情，不使用长期缓存的签名媒体 URL。
4. 下载文件名继续包含稳定的 `note_id`，避免同名标题覆盖。
5. 支持选择当前清晰度下载；格式需要合并时继续使用项目 FFmpeg 流程。
6. 下载完成后本地文件立即可播放，重启后仍能正确识别来源和本地路径。
7. 错误信息区分视频已删除、图文笔记、登录限制、风控验证、媒体地址过期、网络/代理失败和磁盘错误。

### R6：收藏、历史和播放记忆

1. 从首页、搜索、URL、收藏和历史进入的小红书视频使用同一个稳定视频键，例如 `xiaohongshu:<note_id>`。
2. 收藏、历史和下载记录保存正确标题、作者昵称、封面、原始详情 URL 和 `source_site`。
3. 再次从首页、搜索、收藏或历史播放同一视频时恢复播放记忆点。
4. 保存到数据库的规范 URL 应保留足以重新定位笔记的信息，但不长期保存安全签名和媒体直链。
5. 若旧记录中的 token 已失效，播放入口通过 WebEngine 重新获取上下文，不把旧 token 当永久凭据。
6. 删除收藏或历史不删除下载文件，也不影响另一类记录。

### R7：作者视频列表与列表能力

小红书当前 yt-dlp 提取器只稳定提供作者 ID，作者昵称和作者主页需要从首页/搜索卡片或详情数据补齐，作者视频列表接口尚未完成真实分页验证。

推荐口径：

1. 首版必须正确显示当前视频作者昵称和作者 ID。
2. 若同一浏览器安全上下文可以稳定获得作者主页视频流，则把作者视频加载为“播放列表”，支持选择播放、上一条/下一条和自动连播。
3. 作者列表不能稳定验证时，本版本不显示空的伪列表，也不阻止单视频功能交付。
4. 小红书收藏夹、专辑、话题、地点和标签列表不纳入首版。
5. 图文笔记不加入作者视频播放列表。

### R8：风控、验证和错误处理

1. 识别 HTTP 406/403/429、验证码、安全验证页、异常空响应和页面跳转异常。
2. 用户主动加载首页、搜索或播放时需要验证，可显示可见的“小红书安全验证”窗口。
3. 后台预取触发验证时不自动弹窗打断用户，只在页面状态区提示，由用户主动打开。
4. 验证页面必须使用与请求服务相同的 WebEngine Profile，验证完成后只重试原操作一次。
5. 应用不自动破解滑块、验证码或安全挑战，不模拟账号密码登录。
6. 验证期间暂停小红书首页补水、搜索和详情重试，避免并发请求继续加重风控。
7. 用户取消验证时保留当前完整页面和已有结果。
8. 平台错误不得统一折叠为“没有可播放清晰度”。

### R9：缓存、性能和请求预算

1. 首页和搜索卡片元数据可使用内存缓存；首版不要求持久化个性化首页。
2. 卡片缓存可保存 ID、标题、作者、封面、详情页定位信息和获取时间。
3. 动态签名、Cookie、完整请求头和媒体直链不得持久化。
4. `xsec_token` 只在当前会话短期内存中使用，设置明确 TTL；过期后重新获取。
5. 同一操作只允许一个小红书前台请求；首页补水不得与用户搜索、播放详情解析抢占资源。
6. 搜索和首页补足 20 条时设置最大批次数；达到上限后返回明确状态，不无限滚动页面或循环请求。
7. 相同 `note_id` 的并发详情解析合并为一个任务，避免重复打开页面和重复运行 yt-dlp。
8. 站点、Cookie/Profile、代理或登录身份变化时，废弃旧安全上下文缓存。

### R10：安全与隐私

1. 小红书使用独立、首版默认 off-the-record 的 WebEngine Profile，不与抖音 Profile 混用。
2. 主框架导航仅允许经确认的小红书页面；API 和静态资源按域名和用途建立白名单。
3. 页面权限默认拒绝摄像头、麦克风、地理位置、通知、剪贴板和未授权下载。
4. 拦截弹窗和外部跳转；需要打开外部浏览器时必须由用户明确点击。
5. 日志不得记录 Cookie 值、`xsec_token`、安全请求头、完整签名媒体 URL 或大体积原始响应。
6. 错误日志中的详情 URL应移除 query，仅保留 host、路径类型和脱敏 ID。
7. 不把用户 Cookie、URL 或访问行为发送给第三方解析服务。
8. 不默认引入外部收费 API、逆向签名服务或来源不明的抓取 SDK。

### R11：启动操作指南

1. 本版本增加启动操作指南弹窗。默认情况下，每次启动应用都显示，直到用户勾选“下次不再显示”。
2. “第一次启动”的含义是指南正文提醒用户首次使用时应优先完成 Cookie 配置，不是只允许弹窗出现一次。
3. 弹窗应在主窗口完成基本初始化并可见后显示，不得阻塞数据库迁移、播放器初始化或其它启动任务，也不得造成主窗口无响应。
4. 指南主要内容统一为：

   ```text
   首次使用建议先为各视频网站配置 Cookie：

   推荐方法：安装 Firefox，并分别登录 Bilibili、YouTube、抖音、TikTok 和小红书，
   然后进入“设置”，使用“自动检测”获取各站点 Cookie。

   也可以使用浏览器扩展（例如 Get cookies.txt LOCALLY）在本机导出 cookies.txt，
   再进入“设置”，为每个视频网站分别导入并保存。
   ```

5. 站点名称和实际设置项保持一致，不能把 Douyin、TikTok 或 Xiaohongshu Cookie 合并保存。
6. 弹窗提供“前往设置”和“稍后”两个明确操作：
   - “前往设置”关闭弹窗并打开设置页的网站/Cookie 配置区域；
   - “稍后”只关闭本次弹窗，下次启动继续显示。
7. 弹窗提供“下次不再显示”复选框。用户勾选后，无论点击“前往设置”“稍后”还是窗口关闭按钮，都保存隐藏状态，下次启动不再显示。
8. 未勾选复选框时，关闭弹窗不得错误保存隐藏状态。
9. 隐藏状态使用独立配置项保存，例如 `ui.hide_startup_cookie_guide=true`；旧配置中没有该字段时默认显示。
10. 卸载后清除用户配置、重置设置或删除用户配置文件后，指南恢复显示；普通应用升级不得擅自清除用户已经选择的隐藏状态。
11. 弹窗不得读取、显示、记录或上传 Cookie 内容。对于浏览器扩展，只说明“本地导出”方式，不提供来源不明的下载地址，也不引导用户把 Cookie 上传到网页或第三方服务。

## 4. 推荐技术方案

### 4.1 总体方案

推荐采用混合架构：

```text
小红书首页/搜索
    -> Qt WebEngine 同源页面和站点签名环境
    -> 提取卡片元数据、note_id、xsec_token、分页状态
    -> 构造带上下文的详情 URL
    -> 项目内置 yt-dlp XiaoHongShu 提取器
    -> VideoInfo / VideoQuality
    -> libmpv 播放或下载管理器
```

该方案的理由：

- 首页和搜索必须依赖浏览器页面运行时；
- 现有 yt-dlp 已能解析单视频和多档媒体格式，没有必要重复实现；
- WebEngine 只负责平台发现和安全上下文，媒体格式继续走项目成熟链路；
- 站点 API 改动时，首页适配和单视频提取可以分别维护；
- 不依赖第三方服务，也不需要在 Python 中长期维护动态签名算法。

### 4.2 推荐新增组件

建议新增：

```text
services/xiaohongshu_browser_service.py
resolver/xiaohongshu_resolver.py
ui/xiaohongshu_verification_dialog.py
```

`XiaohongshuBrowserService` 负责：

- 创建独立 WebEngine Profile；
- 导入小红书配置对应的浏览器 Cookie；
- 加载 `red_video` 和搜索页面；
- 在文档创建阶段注入受控脚本，观察站点真实 fetch/XHR；
- 捕获 `dual_feed` 和 `search/notes` 响应；
- 保留 cursor、search_id、note_id 和短期 token；
- 检测验证状态并切换到可见验证窗口；
- 串行调度首页、搜索和详情上下文请求；
- 在关闭、切站点或配置变化时取消任务并释放页面。

`XiaohongshuResolver` 负责：

- URL 类型识别和分享短链归一化；
- 首页/搜索响应到 `HomeVideo` 的转换；
- 视频卡片过滤、去重、分页和缓存；
- 构造可靠的详情 URL；
- 调用通用 yt-dlp resolver；
- 把小红书字段映射到 `VideoInfo/PlaylistEntry`；
- token 失效后的单次恢复；
- 小红书特定错误分类。

验证对话框只负责显示同一 Profile 下的平台页面和验证状态，不负责解析业务数据。

### 4.4 Cookie 自动探测

在 `SITE_LOGIN_COOKIES` 中增加小红书域和经过验证的登录标志 Cookie。推荐优先使用：

```text
.xiaohongshu.com / xiaohongshu.com
web_session
id_token
```

自动探测继续只查询 Cookie 的 host 和 name，不读取 value。探测到 Cookie 只代表“浏览器可能已登录”，真正可用性仍由首页轻量探测确认。

### 4.5 首页和搜索采集方式

推荐在页面创建阶段注入最小观察脚本，包装 fetch/XHR 并只把目标接口的结构化结果传回 Python：

- 不修改页面业务逻辑；
- 不伪造用户操作；
- 不导出 Cookie 和安全请求头；
- 不记录完整响应；
- 仅处理已确认的首页和搜索 endpoint；
- 页面接口变化时明确失败，不静默回退到不安全的固定 HTTP 请求。

后续分页优先复用页面自己的请求方法或页面状态。若必须由应用触发同源 fetch，也必须在页面上下文中生成站点要求的签名，不能在 Python 中硬编码签名值。

### 4.6 单视频解析和下载

单视频优先继续使用 `YoutubeResolver` 中已经通用化的 yt-dlp 执行、Cookie 重试、格式整理和错误格式化能力，后续可再重命名为通用 `YtDlpResolver`，但不把重构作为本版本前置条件。

传入 yt-dlp 的 URL 必须保留有效 `xsec_token` 和 `xsec_source`，同时使用小红书站点 Cookie。解析成功后把裸 `note_id` 转成稳定业务 ID，但把含 token URL限制在短期解析上下文中。

### 4.7 作者列表方案

作者列表建议作为第二阶段能力：

1. 先从卡片/详情补全作者昵称、作者 ID 和作者主页 URL。
2. 在 WebEngine 中验证作者主页实际接口、cursor 和视频过滤规则。
3. 验证通过后映射为当前播放器的 creator playlist。
4. 未验证前不调用 yt-dlp 猜测列表，也不把搜索结果冒充作者列表。

## 6. 验收标准

### 6.1 站点与设置

1. 工具栏可在五个站点间切换，紧凑布局不遮挡窗口按钮。
2. 默认首页选择“小红书”后，重启进入小红书视频首页。
3. 小红书默认画质、Cookie 文件、浏览器和 Profile 独立保存，不覆盖其它站点。
4. Cookie 自动探测可识别已登录 Firefox；探测不到时可手动选择或导入 Cookie。
5. Bilibili、YouTube、抖音和 TikTok 现有行为不回归。

### 6.2 首页

1. 有效 Firefox Cookie 和可访问网络下，`red_video` 首页成功显示真实视频卡片。
2. 成功构成完整页时显示 20 个有效视频，且同页无重复 `note_id`。
3. 连续浏览至少 5 页，分页顺序稳定，已显示视频不被后台结果重排。
4. 图文、直播、商品和无效占位卡片不显示。
5. 每张卡片标题、作者昵称和封面与网页内容一致。
6. 点击任意卡片进入播放器，不出现“卡片可见但 token 已被丢弃”的解析失败。
7. 下一页不足 20 条或触发风控时保留当前页，显示明确提示，不展示重复项凑数。
8. 切换站点后返回，小红书当前页和滚动状态可恢复。

### 6.3 搜索

1. 使用至少 3 个中文关键词搜索，结果属于小红书且只显示视频笔记。
2. 搜索第一页目标为 20 个有效视频；若平台可继续返回，支持下一页。
3. 连续加载至少 3 页，同页无重复，旧关键词结果不会覆盖新关键词。
4. 搜索结果卡片可直接播放和收藏。
5. 无结果、未登录、风控和网络失败显示不同提示。

### 6.4 URL 播放

1. 至少验证 10 个公开 `/explore/<note_id>` 视频，其中包含横屏、竖屏、H.264 和 HEVC 样本。
2. 至少验证 3 个 `/discovery/item/<note_id>` 视频。
3. 至少验证 3 个分享短链；若短链真实验证不稳定，则从正式支持清单移除并在 UI 明确提示。
4. 标题、作者昵称、封面、时长和清晰度正确显示。
5. 可正常播放、暂停、Seek、切换清晰度、全屏、小窗、停止和重新播放。
6. 有多档格式时，高/中/低和智能选择行为符合现有统一规则。
7. 图文笔记显示“当前仅支持视频笔记”，不误报为清晰度问题。
8. token 过期后最多自动恢复一次，失败时给出明确原因。

### 6.5 下载

1. 至少下载 5 个小红书视频，包含不同编码和分辨率。
2. 下载列表来源显示“小红书”，完成文件存在且可立即本地播放。
3. 重启应用后下载记录仍指向正确文件和来源，不被识别成 YouTube。
4. 清晰度选择、FFmpeg 合并、取消、重试和失败清理符合现有下载规则。
5. 媒体地址过期时重新解析成功，或显示明确错误，不产生“完成但文件不存在”的记录。

### 6.6 收藏、历史和播放记忆

1. 从首页、搜索、URL、收藏和历史播放同一笔记，稳定识别为同一个视频。
2. 播放超过 30 秒后停止，再从任一入口打开，恢复到记忆点。
3. 收藏和历史显示正确的小红书来源、标题、作者和封面。
4. 重启后收藏、历史和播放记忆仍有效。
5. 旧 token 失效不导致永久无法从收藏或历史播放。

### 6.7 风控和安全

1. 模拟 406/403/429、验证页、空响应和 token 失效，均得到准确错误分类。
2. 用户主动操作触发验证时可打开同一 Profile 的验证窗口，完成后原操作只重试一次。
3. 后台任务触发验证不自动打断用户。
4. 验证期间不会并发发起首页、搜索和详情请求。
5. 页面不能未经用户操作访问外部站点、打开弹窗或取得摄像头、麦克风、位置和通知权限。
6. 日志、缓存、数据库和崩溃上下文中不存在 Cookie 值、token、安全请求头或完整签名媒体 URL。

### 6.8 性能和稳定性

1. WebEngine 冷启动时，正常网络下首页在 15 秒内显示首批结果或明确加载状态。
2. 同一会话再次进入小红书首页时，内存缓存命中应在 2 秒内恢复页面。
3. 搜索前台任务优先于首页补水，不发生两个页面同时高频请求。
4. 快速切站点、连续搜索、关闭应用时，无崩溃、悬空线程和旧响应覆盖。
5. 相同视频的并发解析被合并，不重复启动多个 yt-dlp 进程。

## 8. 待用户审核的推荐裁定项

### A. 首版范围

推荐：首版正式支持视频首页、视频搜索、视频 URL、播放、下载、收藏、历史、播放记忆和设置；图文、直播和互动功能不支持。

### B. 技术路线

推荐：WebEngine 负责首页/搜索和安全上下文，项目内置 yt-dlp 负责单视频媒体解析，libmpv 负责播放；不自研固定签名算法。

### C. 首页和搜索页容量

推荐：UI 目标每页 20 个有效视频；允许受预算限制地补取后续批次，但不足时不使用重复或图文卡片凑数。

### D. Cookie 和登录

推荐：只读取用户现有浏览器 Cookie 或 cookies.txt，不开发账号密码、扫码登录；风控时显示平台原生验证页面。

### E. WebEngine Profile

推荐：首版采用独立、会话级 off-the-record Profile；应用重启后重新导入浏览器 Cookie，不在应用目录长期复制登录状态。

### F. 分享短链

推荐：纳入开发和真实验证；只有 3 个以上不同样本稳定通过后才列为正式支持，否则保留明确“不支持该链接形式”的提示。

### G. 作者视频列表

推荐：作者昵称属于强交付；作者视频列表在接口真实验证稳定后启用，未验证通过不阻塞首版，也不显示空列表。

### H. 动态凭据缓存

推荐：`xsec_token` 仅在当前会话短期内存使用，不进入数据库、持久化缓存和普通日志；收藏/历史保存裸 note ID，播放时重新获取上下文。

### I. 第三方服务

推荐：不引入外部小红书解析 API、收费签名服务或来源不明 SDK，所有用户 Cookie 和访问行为留在本机。

### J. 交付口径

推荐：首页、搜索、单视频播放、下载和播放记忆均作为正式验收项；作者列表为尽力交付；任何已宣称支持的能力必须同时通过调试版和安装版真实环境验证。

## 9. 风险与维护说明

1. 小红书接口、签名、页面结构和风控策略均可能变化，无法承诺永久免维护。
2. 同一 Cookie 在不同 IP、代理、地区或设备环境下可能表现不同。
3. 首页/搜索接口即使 HTTP 200，也可能返回验证状态、空列表或混合内容。
4. yt-dlp 当前提取器依赖详情页初始状态；上游页面改版后可能需要升级 yt-dlp 或增加浏览器详情兜底。
5. `xsec_token` 有时效和上下文属性，不能作为永久视频 URL 的一部分存储。
6. HEVC 高分辨率流在部分系统/显卡上可能无法硬解，需要保留 H.264 格式和 mpv 软件解码回退。
7. 小红书内容以竖屏为主，需要重点回归窗口、全屏、小窗和 DLNA 的比例处理。
8. WebEngine 会增加内存占用，必须延迟初始化、单实例复用，并在站点未使用时避免后台常驻请求。

### 11.3 平台限制与实现裁定调整

当前平台会把不带 `xsec_token` 的裸 `/explore/<note_id>` 和 `/discovery/item/<note_id>` 页面重定向到安全错误页；仅有 Cookie 和 note ID 无法可靠生成新的 token。

实际实现因此采用以下口径：

1. 应用首页、搜索和浏览器“分享/复制链接”产生的完整地址为正式播放入口。
2. 裸 note ID 地址解析失败时快速提示用户取得包含 `xsec_token` 的完整分享地址，不再等待浏览器详情超时。
3. 为保证收藏和历史在 token 有效期内可以继续播放，记录中保留原完整详情 URL。
4. `xsec_token` 仍不得进入普通日志、结构化统计或持久化首页缓存，相关 URL在命令日志中统一显示为 `<security-context>`。
5. token 过期后，用户可从首页/搜索再次打开同一视频，收藏/历史记录会按稳定 `xiaohongshu:<note_id>` 更新为新的地址。

第 3 点是对第 8 节 H 项“完全不持久化 token”的必要调整：平台当前不提供仅凭 note ID 可靠刷新 token 的公开能力。若后续确认可稳定刷新 token，应恢复为数据库只保存裸 note ID。
