# 抖音（Douyin）与 TikTok 支持需求分析、实施方案和验收标准

编制日期：2026-08-27
建议目标版本：`v0.2.29`
状态：**需求已审核通过，裁定项全部采用推荐意见；v0.2.29 已完成编码、自动化测试和真实环境验证**

## 1. 建设目标

在现有 YouTube、Bilibili 支持基础上增加两个独立站点：

- 抖音（Douyin，中国大陆站）；
- TikTok（国际站）。

新增站点需要贯通首页、搜索、URL 播放、用户/合集播放列表、下载、收藏、播放历史、播放记忆、Cookie、默认画质、默认首页、站点切换和设置等现有业务链路。

本批次继续使用 yt-dlp 和 libmpv。针对抖音首页/搜索的动态签名与传输层风控，最终使用应用内置的 Qt WebEngine 隐藏页面执行站点自身签名和请求；不引入账号密码登录、扫码登录、外部浏览器自动化或模拟登录服务。

## 2. 能力与限制分析

### 2.1 当前架构

- `YoutubeResolver` 实际承担通用 yt-dlp 视频解析、格式整理、字幕和下载上下文构建职责。
- `SiteResolver` 负责 Bilibili / YouTube 首页、搜索、播放列表和合集分流。
- 工具栏、设置页、Cookie 探测、默认画质和默认首页大量使用固定的两站点枚举。
- 收藏、历史、下载和播放记忆已经通过 `source_site` / `webpage_url` 具备扩展基础，但站点识别和显示标签仍只认识两站。

### 2.2 yt-dlp 能力核实

当前项目内置 yt-dlp 已列出以下提取器：

- `Douyin`；
- `TikTok`；
- `vm.tiktok`；
- `tiktok:user`；
- `tiktok:collection`；
- `tiktok:live`。

`tiktok:tag`、`tiktok:sound`、`tiktok:effect` 当前存在上游不可用标记，因此不作为本版本承诺能力。

### 2.3 平台客观限制

抖音/TikTok 的推荐流和搜索接口存在动态签名、登录状态、地区限制、频控和风控；其稳定性不能等同于 Bilibili 公开接口或 YouTube ytsearch：

- Cookie、User-Agent、IP 地区和账号状态可能影响结果；
- 无 Cookie 时可能只能解析公开分享 URL，首页/搜索可能为空；
- TikTok 内容可能因地区不可用；
- 抖音分享短链通常需要重定向归一化；
- 平台接口变化可能需要跟随 yt-dlp 升级。

因此首版采用“URL 播放和下载为强验收：首页/搜索为尽力获取并有明确降级提示”的产品口径。

## 3. 功能范围

### 3.1 站点标识与名称

统一站点键：

| 站点 | 内部键 | 中文显示名 | 英文/紧凑名 |
| --- | --- | --- | --- |
| Bilibili | `bilibili` | Bilibili | B站 |
| YouTube | `youtube` | YouTube | YT |
| 抖音 | `douyin` | 抖音 | DY |
| TikTok | `tiktok` | TikTok | TT |

抖音与 TikTok 必须作为两个独立站点保存 Cookie、默认画质、首页缓存和搜索状态，不得合并为一个配置项。

### 3.2 URL 支持

需要识别并归一化：

- 抖音视频页、分享页和短链，例如 `douyin.com/video/...`、`v.douyin.com/...`；
- TikTok 视频页和短链，例如 `tiktok.com/@user/video/...`、`vm.tiktok.com/...`、`vt.tiktok.com/...`；
- TikTok 用户主页；
- yt-dlp 可解析的 TikTok collection URL。

普通视频 URL 必须支持播放、清晰度/格式选择、下载、收藏、历史、播放记忆、浏览器打开和 DLNA 能力判断。

直播、标签页、音效页和特效页不纳入首版正式支持；用户输入时应给出明确的“不支持此链接类型”或上游解析错误提示。

### 3.3 首页

- 工具栏站点选择增加抖音和 TikTok。
- 设置的默认首页增加抖音和 TikTok。
- 切换站点后保留各自首页页码、缓存和滚动状态，逻辑与现有站点一致。
- 首页实现优先使用可验证的站点接口或 yt-dlp 提取结果。
- 未登录、地区限制或风控导致无法加载时，页面显示明确空态：建议使用 URL 播放、配置 Cookie 或切换网络；不得仅显示空白列表。
- 首页加载失败不能影响 URL 播放、收藏、历史和下载等已可用功能。

### 3.4 搜索

- 顶部搜索框在抖音/TikTok 站点下搜索对应平台内容。
- 支持分页或增量加载；若平台只返回一次性结果，则统一在适配层切片，不向 UI 暴露差异。
- 搜索结果至少包含标题、作者、视频 URL、缩略图、时长（数据源提供时）和发布时间（数据源提供时）。
- Cookie/地区/风控导致搜索不可用时显示可操作提示。
- 站点不支持的搜索类型不应回退到 YouTube 搜索，防止串站。

### 3.5 播放和格式

- 复用通用 yt-dlp 视频解析链路，解析 `VideoInfo`、`VideoQuality`、音轨、字幕和 HTTP headers。
- 站点视频 ID 使用带前缀的稳定键，例如 `douyin:<aweme_id>`、`tiktok:<video_id>`。
- 播放请求必须保留 yt-dlp 返回的 User-Agent、Referer、Cookie 等必要请求头。
- 无独立清晰度标签时，根据高度/FPS/码率生成稳定可读的清晰度选项。
- 默认画质支持智能、高、中、低四种模式，并按站点独立保存。
- 播放记忆点从首页、搜索、URL、收藏、历史和播放列表入口共用。

### 3.6 播放列表、用户主页和合集

首版正式支持：

- TikTok 用户主页视频列表（`tiktok:user`）；
- TikTok 可解析合集（`tiktok:collection`）；
- 抖音用户主页/合集仅在当前 yt-dlp 或可验证接口可以稳定解析时启用。

行为要求：

- 用户/合集 URL 识别为播放列表，不按单视频解析；
- 显示标题、作者、条目数、缩略图和条目列表；
- 支持选择播放、上一条/下一条、自动连播、批量下载和保存播放列表；
- 条目不可用、私密或已删除时跳过并标注状态；
- 列表解析失败不影响其中已知单视频 URL 的直接播放。

不承诺 TikTok 标签、音效、特效和直播列表。

### 3.7 下载

- 下载任务记录正确的 `source_site`，列表显示“抖音”或“TikTok”。
- 下载使用站点对应 Cookie、代理、请求头和 yt-dlp extractor。
- 视频/音频分离时沿用 FFmpeg 合并策略；只有单文件格式时直接下载。
- 输出文件名继续包含视频 ID，导入已完成文件时能恢复正确站点和原始 URL。
- Cookie 解密失败时沿用换浏览器、Cookie 文件和 Chromium 解密回退。
- 下载失败信息区分登录限制、地区限制、风控、视频已删除和网络错误。

### 3.8 收藏、历史和播放记忆

- 收藏和历史表保存 `source_site=douyin/tiktok`，站点列显示正确名称。
- 从收藏/历史重新播放时使用对应站点 Cookie 和解析器。
- 播放记忆点按稳定视频 ID和规范化 URL 匹配。
- 删除收藏或历史记录不删除下载文件和另一类记录。
- 批量下载、批量删除和搜索筛选支持两个新站点。

### 3.9 设置

设置页需要扩展为四站点配置：

- 默认首页：Bilibili、YouTube、抖音、TikTok；
- 网站配置：四站点切换；
- 每站点独立默认画质；
- 每站点独立 Cookie 文件、浏览器和 Profile；
- Cookie 自动探测结果按站点保存；
- 代理保持现有全局模式，首版不增加每站点独立代理；
- JS Runtime 保持全局配置，供 yt-dlp 按需使用。

工具栏站点选择器需要适配四项和较小窗口：宽窗口显示全称，紧凑模式显示 B站 / YT / DY / TT；不得挤压关闭、最小化等关键按钮。

### 3.10 Cookie 探测

- 抖音登录 Cookie 识别域包含 `.douyin.com` 等实际站点域；登录标志 Cookie 需通过真实浏览器样本确认。
- TikTok 登录 Cookie 识别域包含 `.tiktok.com`；登录标志 Cookie 同样基于真实样本确认。
- 自动探测只读取 Cookie 域名和名称，不读取值，维持当前隐私边界。
- 无法可靠判定登录态时允许用户手动选择浏览器或导入 cookies.txt。

## 4. 推荐产品裁定

### A. 首页与搜索降级

推荐：URL 播放/下载为必须可靠交付；首页/搜索若因平台限制不可用，显示带操作建议的空态，不阻止版本交付。

### B. 直播

推荐：首版不支持抖音/TikTok 直播播放和下载。即使 yt-dlp 列出 `tiktok:live`，直播涉及刷新地址、结束状态、录制语义和 DLNA 行为，应独立立项。

### C. 标签、音效和特效页

推荐：首版不支持。上游部分提取器当前已标记为不可用。

### D. 抖音用户主页列表

推荐：以当前 yt-dlp/接口真实验证结果决定是否启用；若不稳定，首版仅支持抖音单视频和可解析分享列表，不显示虚假的可用入口。

### E. 下载水印

推荐：默认使用 yt-dlp 提供的最佳无水印或原始媒体格式；无法获得无水印源时下载平台可提供的最佳格式，不额外实现去水印算法。

### F. 登录与验证码

推荐：应用不实现账号密码登录、扫码登录或验证码处理，只读取用户浏览器现有 Cookie 或导入 cookies.txt。

### G. TikTok 地区限制

推荐：不绕过平台地区政策；尊重用户配置的全局代理，并把地区不可用明确呈现为解析失败原因。

## 5. 技术实施方案

### 5.1 站点注册表

新增集中式站点定义模块，至少包含：

- 站点键、显示名和紧凑名；
- URL host 后缀；
- 默认首页能力、搜索能力、播放列表能力；
- Cookie 域和配置键；
- 首页/搜索不可用提示。

逐步替换散落的 `{"youtube", "bilibili"}` 和二选一逻辑，防止新增站点后默默回落到 YouTube。

### 5.2 Douyin/TikTok Resolver

建议新增 `resolver/douyin_tiktok_resolver.py`，内部可分两个适配器：

- URL 分类和短链归一化；
- 调用通用 yt-dlp resolver 解析单视频；
- 解析 TikTok user/collection 列表；
- 首页和搜索适配；
- 稳定视频 ID、作者 ID、作者主页、缩略图、发布时间和来源站点映射；
- 站点特定错误分类和日志脱敏。

通用格式解析继续复用 `YoutubeResolver` 中 yt-dlp 命令、Cookie 重试、字幕和格式整理能力；后续可将该类重命名/拆分为 `YtDlpResolver`，但首版可通过组合方式降低改动风险。

实施结果补充：抖音未签名 JSON 接口即使带有效 Firefox Cookie，仍会因 Python HTTP/TLS 指纹与浏览器身份不一致而频繁返回 `verify_check`。最终新增线程安全的 Qt WebEngine 请求服务，导入已配置浏览器 Cookie，在抖音页面上下文调用 `window.byted_acrawler.frontierSign()` 生成动态签名，再由 Chromium 发起同源请求。搜索按平台原生批次分页；首页复用精选页已加载数据并补充多个签名推荐窗口后去重。TikTok 继续使用已验证的站点接口、缓存条目和 yt-dlp 降级链路。

### 5.3 SiteResolver 分流

- 根据 URL host 精确识别四站点；
- 首页/搜索按站点适配器分派；
- creator/collection 仅在站点声明支持时执行；
- 缓存键继续包含站点、Cookie、代理、页码和关键词；
- 不认识的 URL交由通用 yt-dlp 解析，但来源站点不得错误标记为 YouTube。

### 5.4 UI 与设置

- 工具栏站点选择器由固定两个 radio 重构为数据驱动按钮组；
- 设置页默认首页和网站配置同样数据驱动；
- 四站点草稿字典、保存逻辑、Cookie 文件路径和默认画质配置统一遍历站点注册表；
- 小窗口压缩文本和布局增加回归测试。

### 5.5 数据与兼容

- SQLite 的 `source_site` 为文本，无需新列；现有数据保持不变。
- `detect_source_site()` 和 `source_site_label()` 增加抖音/TikTok host 和标签。
- 下载任务 JSON 保持兼容；旧任务按 URL重新识别站点。
- 备份/恢复需要包含新增 `cookie_douyin.txt`、`cookie_tiktok.txt`，并保持旧备份可恢复。

### 5.6 下载和导入

- `build_download_command()` 必须使用任务 URL对应站点的显式浏览器 Cookie，而非固定 YouTube Cookie。
- 已完成文件导入和视频 ID反推 URL增加 Douyin/TikTok 规则；无法可靠反推时保留本地任务，但不生成错误的 YouTube URL。
- 文件名 ID 清洗规则适配站点前缀。

### 5.7 错误与观测

日志记录站点、提取器、URL 类型、是否使用 Cookie、错误分类和重试阶段，不记录 Cookie 值。

用户提示至少区分：

- 需要登录/Cookie；
- 视频私密、删除或仅好友可见；
- 地区不可用；
- 风控/请求过频；
- 当前链接类型不支持；
- yt-dlp 版本过旧；
- 网络或代理失败。

## 7. 验收标准

### 7.1 站点与设置

1. 工具栏能在四站点间切换，紧凑布局不遮挡窗口关键按钮。
2. 默认首页选择四站点均能在重启后生效。
3. 四站点默认画质、Cookie 浏览器/Profile 和 Cookie 文件独立保存，互不覆盖。
4. Cookie 自动探测结果按站点显示；探测不到时可手动配置。
5. Bilibili/YouTube 现有首页、搜索、播放和下载行为不回归。

### 7.2 抖音 URL

1. 至少验证 5 个公开抖音普通视频 URL和 3 个分享短链可解析播放。
2. 标题、作者、缩略图、时长和可用清晰度正确显示（数据源提供时）。
3. 播放、暂停、Seek、全屏、小窗、停止和重新播放正常。
4. 下载成功，文件可本地播放，下载列表来源显示“抖音”。
5. 收藏、历史、播放记忆点和浏览器打开正常。
6. 私密/删除/需要登录视频显示明确错误。

### 7.3 TikTok URL

1. 至少验证 5 个公开 TikTok 普通视频 URL、3 个 `vm/vt.tiktok.com` 短链。
2. 在可访问地区/代理环境下完成播放和下载。
3. 请求头、Cookie 和重定向处理正确，不出现解析成功但媒体 403。
4. 收藏、历史、播放记忆和来源标签正常。
5. 地区不可用时给出明确提示，不误报为“没有清晰度”。

### 7.4 播放列表

1. 至少验证 2 个 TikTok 用户主页，可列出条目并选择播放。
2. 至少验证 1 个 yt-dlp 可解析 TikTok collection。
3. 列表支持上一条/下一条、自动连播、批量下载和保存。
4. 私密/已删除条目被跳过或标注，不阻断其它条目。
5. 抖音用户/合集能力按真实验证结果启用；未通过验证时 UI 不宣称支持。

### 7.5 首页与搜索

1. 有效 Cookie 和网络环境下，抖音/TikTok 首页能展示真实可播放内容，或按裁定显示明确降级空态。
2. 搜索结果与所选站点一致，不串到 YouTube/Bilibili。
3. 分页/增量加载不会重复或覆盖其它站点缓存。
4. 无 Cookie、风控和地区限制场景均有可操作提示。

### 7.6 下载、数据和升级

1. 单视频和播放列表批量下载使用正确站点 Cookie。
2. 收藏、历史、下载任务和已保存播放列表重启后保留正确站点。
3. 备份/恢复包含新增 Cookie 文件，旧版备份仍可恢复。
4. 安装版和便携版均能解析/下载两个新站点，不依赖源码目录资源。

### 7.7 测试与质量门槛

- 新增站点识别、URL 分类、模型映射、设置隔离、Cookie 路由、工具栏布局、播放列表和错误分类测试。
- 现有全量自动化测试全部通过。
- `compileall`、`git diff --check` 和打包构建检查通过。
- Windows 安装版、Windows 便携版至少各完成一次真实环境验收；Linux 在可访问网络环境下完成 URL 播放和下载冒烟测试。

## 8. 最终裁定结果

用户已审核，8.1 至 8.7 全部采用推荐意见：

1. 首页/搜索采用“尽力获取 + 明确降级”；URL 播放和下载作为强验收能力。
2. 首版不支持抖音/TikTok 直播。
3. 首版不支持标签、音效和特效页。
4. 抖音用户主页/合集仅在真实验证通过后启用；未通过时 UI 不宣称支持。
5. 不开发账号密码、扫码或验证码登录，仅使用浏览器 Cookie 或 `cookies.txt`。
6. 默认下载 yt-dlp 能取得的最佳无水印/原始格式，不实现额外去水印算法。
7. 继续使用全局代理，不新增每站点独立代理。

上述裁定构成 R1-R5 编码、测试、真实环境验收和发布说明的正式基线；用户另行指示后启动编码。
